# Telegram AI 群聊伙伴 · 部署与配置操作说明

本文档面向运维与部署人员，说明如何准备环境、配置 `.env`、构建启动、验证、升级与备份，
并逐字段解释所有环境变量用途。所有 env 字段的完整注释见仓库根目录 `.env.example`。

---

## 1. 环境与前置条件

- 一台能访问 **Telegram Bot API** 与 **New API 网关** 的 Linux 服务器。
- 已安装 **Docker Engine** 与 **Docker Compose 插件**（v2）。
- 已通过 [@BotFather](https://t.me/BotFather) 创建机器人并取得 Token。
- 一个可用的 New API 网关地址、令牌与模型 ID。

---

## 2. 准备机器人身份

1. 在 BotFather 用 `/newbot` 创建机器人，保存 `TELEGRAM_BOT_TOKEN`。
2. 用 `/setprivacy` 选择该机器人并设为 `Disable`，以接收普通群消息；
   已加入的群可移除后重新添加验证。
3. 确认机器人允许加入群组并具有发送消息权限（通常无需管理员权限）。

> Telegram 消息可见性由隐私模式与群权限共同决定。
> 参考 [Bots FAQ](https://core.telegram.org/bots/faq#what-messages-will-my-bot-get) 与 [Privacy mode](https://core.telegram.org/bots/features#privacy-mode)。

---

## 3. 配置文件 `.env`

```bash
cp .env.example .env
chmod 600 .env        # 含 Token/Key，限制权限
nano .env
```

必须至少填写 4 个必填项：

- `TELEGRAM_BOT_TOKEN`：BotFather 提供的 Token
- `NEW_API_BASE_URL`：网关地址（通常以 `/v1` 结尾，以实际部署为准）
- `NEW_API_KEY`：网关令牌
- `NEW_API_MODEL`：网关可用的模型 ID

管理身份使用 Telegram **数字用户 ID**。不知道自身 ID 时，可先留空白名单启动，
私聊 `/start` 获取 ID 后再填入 `TELEGRAM_OWNER_IDS`。所有者和指定管理员可执行群管理命令；
普通 Telegram 群管理员不会自动获得权限。

> 修改 `.env` 后必须重建容器（`docker compose up -d --force-recreate` 或 `--force-recreate`）；
> `docker compose restart` 不会重新加载环境变量。

## 4. 环境变量逐字段说明（部署必读）

> 以下每个字段都标注了“用途 / 默认值 / 取值范围 / 注意事项”，与 `.env.example` 注释一致。

### 4.1 Telegram 身份与权限
| 变量 | 默认值 | 用途 / 说明 |
| --- | --- | --- |
| `TELEGRAM_BOT_TOKEN` | 必填 | BotFather Token，连接 Telegram Bot API 并收发消息；泄露后 `/revoke` 重置 |
| `TELEGRAM_ALLOWED_CHAT_IDS` | 空 | 允许工作的群数字 ID（逗号分隔、负整数）；留空拒绝所有群的 AI 与上下文存储 |
| `TELEGRAM_OWNER_IDS` | 空 | 所有者用户 ID（正整数、逗号分隔）；拥有 `/stats global` 与全部管理命令 |
| `TELEGRAM_ADMIN_IDS` | 空 | 管理员用户 ID（正整数、逗号分隔）；拥有群管理命令，但无全局统计权限 |

### 4.2 AI 网关
| 变量 | 默认值 | 用途 / 说明 |
| --- | --- | --- |
| `NEW_API_BASE_URL` | 必填 | 网关 Base URL（http(s)，通常 `/v1` 结尾），不含凭证/查询参数 |
| `NEW_API_KEY` | 必填 | 网关访问令牌；权限与额度由网关侧控制 |
| `NEW_API_MODEL` | 必填 | 回复模型 ID，须为网关实际可用的模型标识符 |
| `DECISION_MODEL` | 空 | 决策模型 ID；留空复用 `NEW_API_MODEL`，可用更便宜的小模型降本 |

### 4.3 行为与上下文
| 变量 | 默认值 | 用途 / 说明 |
| --- | --- | --- |
| `BOT_PERSONA` | 自然、友善、有幽默感的中文群聊伙伴 | 性格系统提示词，最长 4000 字符；群内可 `/settings persona` 覆盖 |
| `CONTEXT_MAX_MESSAGES` | 30（1–200） | 每群（话题隔离）保留最近消息条数 |
| `CONTEXT_MAX_CHARS` | 16000（500–100000） | 每群发送给模型的上下文字符预算 |
| `MESSAGE_MAX_CHARS` | 2000（100–10000） | 单条输入内容字符上限，超出忽略 |
| `HISTORY_RETENTION_DAYS` | 7（1–365） | 历史内容与去重标记保留期限 |
| `DECISION_ENABLED` | true | 是否启用 AI 第二级发言判定；关闭仍执行本地规则与硬限频 |
| `DECISION_CONFIDENCE_THRESHOLD` | 0.65（0–1） | 决策回复置信度阈值，达标才回复（模型自评） |
| `DECISION_JSON_MODE` | false | 是否发送 `response_format={"type":"json_object"}`，仅网关支持时开启 |

### 4.4 接话频率与限频
| 变量 | 默认值 | 用途 / 说明 |
| --- | --- | --- |
| `REPLY_PROBABILITY` | 0.35（0–1） | 普通候选进入决策前的采样率；直接触发不受此影响 |
| `DIRECT_MENTION_ALWAYS_REPLY` | true | 直接 @/回复机器人时跳过采样与 AI 决策直接回复（仍受硬限频） |
| `MIN_REPLY_INTERVAL_SECONDS` | 20（≥0） | 同群 AI 回复最短间隔，防刷屏 |
| `CHAT_COOLDOWN_SECONDS` | 8（≥0） | 同群模型处理尝试冷却；跳过/失败也冷却 |
| `MAX_REPLIES_PER_HOUR` | 12（1–3600） | 同群滚动一小时 AI 发送尝试上限，失败/429 也计数 |
| `MESSAGE_BATCH_WINDOW_SECONDS` | 3（0–10） | 连续消息合并窗口 |
| `MESSAGE_MAX_AGE_SECONDS` | 300（10–86400） | 忽略超龄积压消息，避免重启后接旧讨论 |
| `REPLY_DELAY_MIN_SECONDS` | 1（0–30） | 发言前随机等待下限，须 ≤ 上限 |
| `REPLY_DELAY_MAX_SECONDS` | 3（0–30） | 发言前随机等待上限 |

### 4.5 时区、连续追问与每日预算
| 变量 | 默认值 | 用途 / 说明 |
| --- | --- | --- |
| `BOT_TIMEZONE` | Asia/Shanghai | 安静时段、自然日预算、统计使用的 IANA 时区 |
| `FOLLOWUP_TTL_SECONDS` | 120（0–1800） | 成功回复后同用户同话题免 @ 连续追问窗口；0 关闭 |
| `CHAT_DAILY_CALL_LIMIT` | 200（0–100000） | 每群每日请求尝试上限（含决策/回复/失败/重试）；0 禁用该群 |
| `GLOBAL_DAILY_CALL_LIMIT` | 1000（0–1000000） | 全局每日请求尝试上限；0 禁用所有群调用 |
| `USAGE_RETENTION_DAYS` | 30（1–365） | 调用及处理结果统计保留天数，独立于聊天上下文清理 |

### 4.6 计费单价（费用估算用）
| 变量 | 默认值 | 用途 / 说明 |
| --- | --- | --- |
| `AI_INPUT_PRICE_PER_MILLION` | 0（≥0） | 通用输入 Token 单价（美元/百万）；0 表示未配置估价 |
| `AI_OUTPUT_PRICE_PER_MILLION` | 0（≥0） | 通用输出 Token 单价（美元/百万） |
| `DECISION_INPUT_PRICE_PER_MILLION` | 继承通用 | 决策输入单价；留空继承通用单价 |
| `DECISION_OUTPUT_PRICE_PER_MILLION` | 继承通用 | 决策输出单价；留空继承通用单价 |

> 费用以网关返回用量 × 单价估算，**非**网关账单或余额；单价缺失或网关未返回完整用量时相应调用不计入。

### 4.7 模型调用与并发
| 变量 | 默认值 | 用途 / 说明 |
| --- | --- | --- |
| `AI_TIMEOUT_SECONDS` | 30（0–300） | 单次调用总超时（含重试） |
| `AI_MAX_RETRIES` | 2（0–5） | 应用额外重试次数；每次重试独立计入每日预算 |
| `AI_MAX_OUTPUT_TOKENS` | 300（1–4000） | 回复输出 Token 上限，控制单条长度 |
| `AI_MAX_CONCURRENT_REQUESTS` | 4（1–32） | 进程级模型调用并发上限 |
| `AI_TOKEN_PARAMETER` | max_tokens | Token 参数名；网关不支持 `max_tokens` 时改为 `max_completion_tokens` |

### 4.8 存储、日志与健康检查
| 变量 | 默认值 | 用途 / 说明 |
| --- | --- | --- |
| `DATABASE_PATH` | data/bot.db（Compose 覆盖 /app/data/bot.db） | SQLite 路径，保存上下文/设置/统计 |
| `LOG_LEVEL` | INFO | 日志级别 DEBUG/INFO/WARNING/ERROR/CRITICAL |
| `HEARTBEAT_PATH` | data/bot-heartbeat（Compose 覆盖 /tmp/bot-heartbeat） | 心跳文件；本地/Windows 改回数据目录 |
| `HEALTHCHECK_MAX_AGE_SECONDS` | 180（60–600） | 心跳最大允许年龄；超时判定 `unhealthy` |

> Compose 固定覆盖 `DATABASE_PATH=/app/data/bot.db` 与 `HEARTBEAT_PATH=/tmp/bot-heartbeat`。
> 本地开发请把 `HEARTBEAT_PATH` 改回 `data/bot-heartbeat`。

## 5. 构建、检查与启动

```bash
# 仅验证 Compose 配置（不展开输出密钥）
docker compose config --quiet

# 构建镜像
docker compose build

# 仅检查配置，不发 Telegram 消息、不请求模型
docker compose run --rm --no-deps telegram-ai-bot python -m app.check_config

# 后台启动
docker compose up -d
docker compose ps
docker compose logs --tail=100 telegram-ai-bot
```

### 网关兼容性探测（会产生真实费用）

```bash
docker compose run --rm --no-deps telegram-ai-bot python -m app.check_config --probe
```

`--probe` 是独立的连通性检查，不使用生产机器人的每日预算，也不写入生产统计；
仍会向网关发送真实请求，费用以网关记录为准。

> 若网关/模型不支持 `max_tokens`，将 `AI_TOKEN_PARAMETER` 改为 `max_completion_tokens`。
> 默认不发送 JSON 模式参数；确认决策模型支持 `response_format={"type":"json_object"}` 后才开启 `DECISION_JSON_MODE`。

## 6. 配置允许工作的群

1. 填好 `TELEGRAM_OWNER_IDS` 并重建容器（`docker compose up -d --force-recreate`）。
2. 将机器人加入测试群，由所有者/管理员发送 `/chatid` 获取群 ID（未列入白名单的群也可用）。
3. 编辑 `.env`：

```dotenv
TELEGRAM_OWNER_IDS=123456789
TELEGRAM_ALLOWED_CHAT_IDS=-1001234567890,-1009876543210
```

4. 群白名单为空时，**所有群均不触发 AI，也不保存群聊上下文**。
5. 修改 `.env` 后执行 `docker compose up -d --force-recreate` 重载。

> 私聊仅用于说明与身份查询，不提供 AI 陪聊。`docker compose restart` 不会重载环境变量。

## 7. 升级、备份与停止

### 升级（代码或提示词更新）
```bash
docker compose build
docker compose up -d
docker compose logs --tail=100 telegram-ai-bot
```
升级采用 `CREATE TABLE IF NOT EXISTS`，不删原有数据；旧 `.env` 缺字段时用默认值。

### 查看实时状态
```bash
docker compose logs -f telegram-ai-bot
docker inspect --format '{{json .State.Health}}' telegram-ai-companion
docker inspect --format '{{.RestartCount}}' telegram-ai-companion
```

### 备份（先停写再复制整个数据目录）
```bash
umask 077
mkdir -p backups
docker compose stop
docker compose cp telegram-ai-bot:/app/data "./backups/data-$(date +%Y%m%d-%H%M%S)"
docker compose up -d
```
备份包含群聊内容，应限制权限（含 `umask 077`）。

### 恢复与停止
- 恢复：停服务后将整个备份数据目录恢复到原卷，确保所有权 `10001:10001`；勿用旧库覆盖运行中的 SQLite。
- 普通停止：`docker compose stop`。
- 移除容器：`docker compose down`（命名卷保留）。
- **`docker compose down -v` 会删除数据卷及聊天历史，慎用。**

## 8. 持久化、隐私与运行约束

- SQLite 用持久化卷（`bot_data`）保存上下文、去重、暂停、群设置、限频与统计；清理不清零最近一小时配额或当天预算。
- 容器以 UID/GID `10001:10001` 运行，根文件系统只读，仅数据卷与 tmpfs 可写。
- 群里应说明机器人会将最近聊天内容交给配置的 AI 网关处理；日志不含聊天全文、Token 或网关错误正文。
- **同一 Bot Token 只运行一个轮询进程**；勿本地与服务器同时启动，勿增加 Compose 副本。长轮询与 Webhook 不能并用；若 Token 已配置 Webhook，需先移除旧部署 Webhook。
- 去重受保留期限约束，非无限期；进程崩溃与网络发送之间不保证“恰好一次”交付。
- 健康检查仅在成功收到 `getUpdates` 时刷新心跳；群里无人说话仍可健康，Telegram 持续不可达会使心跳过期。它不验证网关/额度/每次回复成功率。Docker `restart` 策略重启退出进程，不因 `unhealthy` 自动重启；应结合日志与外部监控处理持续故障。

### 改用宿主机 `./data` 目录
```bash
mkdir -p data
sudo chown 10001:10001 data
sudo chmod 700 data
```
并把 Compose 的卷挂载改为 `./data:/app/data`。命名卷与绑定目录是不同数据位置，切换前需备份并迁移原数据库。

## 9. 本地开发与测试

### Linux / macOS
```bash
python3.12 -m venv .venv
. .venv/bin/activate
python -m pip install --require-hashes -r requirements-dev.txt
cp .env.example .env
python -m app.check_config
python -m pytest
python -m ruff check .
python -m app.main
```

### Windows PowerShell
```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install --require-hashes -r requirements-dev.txt
Copy-Item .env.example .env
# 编辑 .env，将 HEARTBEAT_PATH 设为 data/bot-heartbeat
.\.venv\Scripts\python.exe -m app.check_config
.\.venv\Scripts\python.exe -m pytest
.\.venv\Scripts\python.exe -m ruff check .
.\.venv\Scripts\python.exe -m app.main
```

> 自动测试使用临时数据库与模型/Telegram 测试替身，不需真实 Token，不发送真实群消息。
> 运行真实机器人仍需有效配置，且须先停止服务器上同 Token 的实例。

依赖锁定文件由 `scripts/lock_tested_environment.py` 从通过测试的 Python 3.12 环境生成；
修改 `requirements.in` / `requirements-dev.in` 后也可用 pip-tools 重新解析再测试。

## 10. 验收清单（建议在测试群逐项确认）

1. 私聊 `/start` 有响应并取得用户 ID；未配置管理员不能执行群管理命令。
2. 白名单为空或群未授权时，普通消息与 @消息均不触发模型。
3. 允许群内 @/回复机器人正常回复；普通成员互聊不会每条响应。
4. 连续多条消息只产生合并后的处理，直接 @ 也不能突破间隔或配额。
5. `/pause` 后不再保存新上下文与发送 AI 回复，重启仍暂停；`/resume` 恢复。
6. 重启后上下文与限频状态仍在；不同群及论坛话题不共享上下文。
7. 临时配置不存在的模型/不可访问网关，确认日志记失败类型，群内不刷报错。
8. 用 `/settings` 与模式按钮调整某群，其他群不受影响；重启覆盖项仍在，`reset` 能恢复默认。
9. 同成员同话题连续追问可免 @；其他成员/话题/回复他人/过期不误触发，结束信号能停当前会话。
10. 设置短暂安静时段并确认 @ 也不调模型，同时 `/context` 仍增长；时段结束恢复正常。
11. 测试群设较小 `daily_call_limit`，确认决策/回复/重试都计数，额度耗尽不再请求；重启保留额度，普通管理员不能看 `/stats global`。
